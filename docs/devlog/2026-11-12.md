# Devlog: Milestone 2 Complete - Vulkan Memory Allocator (VMA) Integration

**Date:** November 12, 2026
**Engine Architecture:** Vulkan 1.3 (C++ RAII), Dynamic Rendering, VMA
**Current State:** Milestone 2 COMPLETE. The engine now features fully automated GPU memory management, stable 3D depth testing, an FPS camera, and ImGui integration with zero memory leaks and zero validation errors.

## Overview

The final objective for Milestone 2 was to replace manual GPU memory management (using raw `vkAllocateMemory` and `vkBindImageMemory`/`vkBindBufferMemory`) with AMD's Vulkan Memory Allocator (VMA). This ensures optimal memory sub-allocation, prevents fragmentation, and abstracts away the complexities of querying device memory properties.

## Work Completed

### 1\. VMA Integration \& Build Setup

* Successfully pulled VMA via `vcpkg` (`vulkan-memory-allocator:x64-windows`) and linked it using CMake.
* Isolated the `#define VMA\_IMPLEMENTATION` macro into a dedicated translation unit (`vma.cpp`) to prevent One Definition Rule (ODR) violations and linker errors.

### 2\. Allocator Initialization with Dynamic Dispatch

* Configured `VmaAllocatorCreateInfo` to work seamlessly with `vulkan.hpp` dynamic dispatchers.
* Extracted raw C-style function pointers directly from the RAII `vk::raii::Instance` using `.getProcAddr()` to feed into `VmaVulkanFunctions`.

### 3\. Resource Refactoring

* **Vertex \& Index Buffers:** Replaced `vk::raii::Buffer` and `vk::raii::DeviceMemory` with VMA's `VkBuffer` and `VmaAllocation`. Utilized `VMA\_ALLOCATION\_CREATE\_MAPPED\_BIT` to map CPU memory instantly without explicit map/unmap calls.
* **Depth Buffer:** Transitioned the depth attachment creation to `vmaCreateImage`, requesting `VMA\_MEMORY\_USAGE\_AUTO\_PREFER\_DEVICE` to guarantee placement in the fastest available GPU VRAM.

## Technical Challenges \& Resolutions

### Issue #1: Null Pointer Assertion in `vmaCreateAllocator`

* **Problem:** VMA triggered a runtime assertion (`VMA\_ASSERT`) when checking the provided Vulkan function pointers, indicating they were `NULL`. This happened because we initially relied on `VULKAN\_HPP\_DEFAULT\_DISPATCHER`, which hadn't properly populated the raw C-pointers VMA expected.
* **Solution:** Bypassed the default dispatcher and fetched the raw memory addresses directly from the OS/Driver using `reinterpret\_cast<PFN\_vkGetInstanceProcAddr>(vulkanInstance.instance.getProcAddr("vkGetInstanceProcAddr"))`.

### Issue #2: C++ Syntax Trap (`->` vs `.`) on RAII Objects

* **Problem:** Attempting to call `.getProcAddr()` using the arrow operator (`->`) resulted in compiler errors (`E0304`).
* **Solution:** Recognized that `vulkanInstance.instance` is a direct object (`vk::raii::Instance`), not a pointer. Corrected the syntax to use the dot operator (`.`).

### Issue #3: Multi-Definition Linker Error (`LNK2005`)

* **Problem:** Including `vma.h` (with `VMA\_IMPLEMENTATION` defined) in multiple headers (`vlk.h`, `Window.h`) caused the compiler to generate duplicate symbols for the entire VMA library.
* **Solution:** Created a standalone `vma.cpp` containing only `#define VMA\_IMPLEMENTATION` and `#include "vma.h"`. All other files now just include the header normally.

### Issue #4: Memory Leak Assertion on Shutdown (`VMA\_ASSERT\_LEAK`)

* **Problem:** Closing the application triggered a breakpoint at `VMA\_ASSERT\_LEAK(!m\_pMetadata->IsEmpty())`.
* **Solution:** The C++ destructor was destroying the `VmaAllocator` *before* destroying the allocated buffers and images. Reordered the `\~vlk()` destructor sequence to explicitly free the Vertex Buffer, Index Buffer, and Depth Image via `vmaDestroyBuffer` and `vmaDestroyImage` **prior** to calling `vmaDestroyAllocator`.
