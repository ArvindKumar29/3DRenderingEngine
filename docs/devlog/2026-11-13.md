# Engine Devlog — November 13, 2026

**Milestone 3 (Phase 1): Real-Time CPU \& GPU Profiling with Tracy**

\---

## 1\. Overview

Today kicked off **Milestone 3** by integrating the **Tracy Profiler (`v0.14.1`)** into the engine. Before adding heavy asset pipelines (`stb\_image` textures and `fastgltf` 3D meshes), establishing a real-time telemetry baseline for both CPU frame times and GPU command buffer execution was essential.

\---

## 2\. Features Implemented

### Build System \& Dependency Integration

* Configured `Tracy::TracyClient` in `CMakeLists.txt` via `vcpkg` (`x64-windows-static-md`).
* Enabled profiling macros across the engine target using `TRACY\_ENABLE`.
* Synced the standalone `tracy-profiler.exe` server (`v0.14.1`, Protocol `82`) with the embedded client library.

### CPU Profiling

* Instrumented the main application loop in `vlk::run()` with `FrameMark` to slice continuous execution into discrete frame timelines.
* Added `ZoneScoped` macros across core engine lifecycle functions (`vlk::init`, `vlk::run`, `vlk::renderFrame`, and `vlk::\~vlk`) to monitor CPU bottlenecks and teardown overhead.

### Vulkan GPU Profiling

* Integrated `<tracy/TracyVulkan.hpp>` to hardware-profile Vulkan command buffers using GPU timestamp queries.
* Initialized `TracyVkCtx` during engine startup and ensured proper cleanup via `TracyVkDestroy` prior to VMA teardown.
* Instrumented the main command buffer recording loop with:

  * `TracyVkCollect(tracyContext, \*cmdPool.cmdBuffer)` to harvest query results from previous frames.
  * `TracyVkZone(tracyContext, \*cmdPool.cmdBuffer, "Main GPU Render Pass")` to measure the exact hardware execution time of image layout transitions, geometry drawing, and ImGui rendering.

## 3\. Technical Challenges \& Root Cause Analysis

### Challenge 1: `VK\_NO\_PROTOTYPES` vs. Raw C Vulkan Calls

Because the engine uses `vulkan\_raii.hpp` (`VULKAN\_HPP\_DEFAULT\_DISPATCHER`), `VK\_NO\_PROTOTYPES` is defined globally. However, `TracyVulkan.hpp` relies on raw C Vulkan calls (`vkCreateQueryPool`, `vkCmdWriteTimestamp`, `vkCmdResetQueryPool`), resulting in `C3861: identifier not found` compilation errors.

### Challenge 2: Static Linkage Collision Between `volk` and `ImGui`

Attempting to expose global C function pointers via `volk` caused an immediate `0xC0000005` Access Violation (DEP violation) inside `ImGui\_ImplVulkan\_Init` when loading Dynamic Rendering functions (`vkGetDeviceProcAddr`):

* **Root Cause:** `vcpkg` pre-compiles `imgui.lib` without `IMGUI\_IMPL\_VULKAN\_USE\_LOADER` (leaving `ImGui\_ImplVulkan\_LoadFunctions` as a no-op stub) and expects standard exported symbols from `vulkan-1.lib`.
* Linking `volk` replaced those function symbols with global function pointer variables residing in the `.data` segment, causing `imgui.lib` to jump to a non-executable data address.

### The Solution: `TRACY\_VK\_USE\_SYMBOL\_TABLE`

Instead of polluting the global symbol table with `volk`, we leveraged Tracy's internal dynamic symbol table loader:

1. Removed `volk` completely so `ImGui` and `vulkan-1.lib` operate natively with Vulkan 1.3 Dynamic Rendering (`UseDynamicRendering = true`).
2. Defined `#define TRACY\_VK\_USE\_SYMBOL\_TABLE` prior to including `<tracy/TracyVulkan.hpp>`.
3. Passed `vkGetInstanceProcAddr` and `vkGetDeviceProcAddr`—fetched directly from our `vk::raii::Instance` (reusing the pointers already resolved for `VmaVulkanFunctions`)—into `TracyVkContext`:

```cpp
tracyContext = TracyVkContext(
    \*vulkanInstance.instance,
    \*device.physicalDevice,
    \*device.logicalDevice,
    \*device.graphicsQueue,
    \*cmdPool.cmdBuffer,
    vmaVulkanFunctions.vkGetInstanceProcAddr,
    vmaVulkanFunctions.vkGetDeviceProcAddr
);
```

## 4\. Profiling Metrics \& Baseline Results

With both CPU and GPU timelines active in Tracy:

* **CPU `vlk::renderFrame` Time:** $\\approx 5.8\\ \\text{ms}$ on VSync-bound frames (down to $812.2\\ \\mu\\text{s}$ on unblocked frames).
* **GPU `Main GPU Render Pass` Execution Time:** $93.41\\ \\mu\\text{s}$ ($100%$ self time).
* **CPU Command Buffer Setup Time:** $40.22\\ \\mu\\text{s}$.
* **Memory Footprint:** $\\approx 68.2\\ \\text{MB}$.
