# Devlog: Milestone 2 (Part 1) - Core Systems, Camera, and ImGui Integration

**Date:** November 4 & 5, 2026

**Engine Architecture:** Vulkan (C++ RAII), GLFW, Volk

**Current State:** 3D Environment with Interactive FPS Camera, Push Constants, and Dear ImGui Debug UI

## Overview

The objective of this development phase was to transition from a static graphics pipeline to an interactive 3D rendering environment. The implementation focused on building a custom Input System, an FPS Camera, utilizing Push Constants for matrix transformations, and integrating Dear ImGui for real-time debugging.

## Work Completed

### 1. Input System & FPS Camera

* **Input Handling:** Abstracted GLFW window events into a dedicated `Input` class. Configured real-time state tracking for key inputs (`W A S D`) and calculated mouse deltas for camera orientation.

* **Camera Mathematics:** Implemented a First-Person Shooter (FPS) camera model.

  * Calculated `View` and `Projection` matrices utilizing `glm`.

  * Implemented Pitch and Yaw constraints to prevent gimbal lock.

  * Dynamically calculated local Right, Up, and Front vectors using cross products to ensure accurate translations.

### 2. Push Constants (MVP Pipeline)

* Refactored the graphics pipeline to support dynamic transformations rather than hardcoded vertex data.

* Updated vertex shaders to accept a `PushConstant` block containing `Model`, `View`, and `Proj` matrices (totaling 192 bytes).

* Mapped camera movements to the 3D space by updating push constants per frame during command buffer recording.

### 3. Dear ImGui Integration (v1.93)

* Configured the build system (vcpkg) to include ImGui with Vulkan and GLFW backends.

* Integrated the UI render pass into the engine's main loop, ensuring compatibility with the existing `VK_KHR_dynamic_rendering` setup.

* Enabled native Volk compatibility within ImGui headers to handle dynamic function loading.

## Technical Challenges & Resolutions

The following technical issues were identified and resolved during this development phase:

### Issue #1: ImGui v1.93 API Updates for Dynamic Rendering

* **Problem:** In ImGui v1.93, configuring dynamic rendering via a direct `ColorAttachmentFormat` assignment in `ImGui_ImplVulkan_InitInfo` is deprecated.

* **Solution:** Initialized the required nested struct by configuring a persistent `ImGui_ImplVulkan_PipelineInfo` object, setting its `sType` to `VK_STRUCTURE_TYPE_PIPELINE_RENDERING_CREATE_INFO_KHR`, and passing a pointer to a persistent `VkFormat` class member variable.

### Issue #2: Access Violation Exception (`0xC0000005`) during Pipeline Creation

* **Problem:** The NVIDIA driver (`nvoglv64.dll`) threw an access violation exception during `vkCreateGraphicsPipelines`.

* **Solution:** The `ImGui_ImplVulkan_InitInfo` struct was zero-initialized. Consequently, `MSAASamples` defaulted to `0`, which is invalid in the Vulkan specification. Explicitly setting `pipelineInfo.MSAASamples = VK_SAMPLE_COUNT_1_BIT;` resolved the pipeline creation failure.

### Issue #3: Pipeline Layout Configuration for Push Constants

* **Problem:** Push constants were submitted to the command buffer without being explicitly declared in the pipeline layout, which can lead to undefined behavior or memory corruption.

* **Solution:** Configured the `vk::PushConstantRange` within the `vk::PipelineLayoutCreateInfo`, specifying the appropriate stage flags, offset, and size requirements.

### Issue #4: RAII Object Lifecycle Management (Descriptor Pool)

* **Problem:** The descriptor pool was declared as a non-RAII `vk::DescriptorPool` handle but initialized with a function returning a `vk::raii::DescriptorPool`. The temporary RAII object was destroyed immediately after the statement execution, leaving a dangling pointer.

* **Solution:** Re-declared the class member as `vk::raii::DescriptorPool pool = nullptr;` to bind the object's lifetime to the `UI` class and ensure safe initialization and destruction.

### Issue #5: Unresolved External Symbol (`LNK2001`) with Vulkan-Hpp Dispatcher

* **Problem:** The linker failed to resolve `defaultDispatchLoaderDynamic` required by `vulkan.hpp`.

* **Solution:** Allocated storage for the dynamic dispatcher by defining the `VULKAN_HPP_DEFAULT_DISPATCH_LOADER_DYNAMIC_STORAGE` macro in a single translation unit (`vlk.cpp`).
